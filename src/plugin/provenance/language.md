## Overlaps resolved

- Blocking in async code. Competing: `ce-code-review` performance persona (11, as a speed problem) and its Swift persona (41, as a frozen interface). Winner: the frozen-interface framing, because it names a run-time effect; the per-language detail comes from the Rust and Python references.
- Type escapes. Competing: `ce-code-review` maintainability persona (40), thermos (101) and `pr-review-toolkit` type-design analyzer. Split: an escape applied to outside data that can crash later is here; the design of the type is the architecture reviewer's.
- Clean-up of listeners and timers. Competing: the `ce-code-review` frontend-races persona (7-8) and the correctness reviewer's resource-release bullet (reliability persona 15). Split: teardown owed to a framework lifecycle (an effect, a mount hook, an event listener) is here; any other resource not released is the correctness reviewer's.
- Panics against swallowed errors. Competing: `pr-review-toolkit` silent-failure hunter (27, all error handling in one reviewer) and the lane's split. Winner: the split; a panic on a fallible path is here, a discarded error is the correctness reviewer's.
- Calls across a framework bridge. Competing: the correctness reviewer's contract checks (`ce-code-review` adversarial persona 40-43) and this reviewer's framework rules. Split: whether the bridge can deliver the call at all (registration, key mapping, managed state) is here; a delivered call with the wrong shape or meaning is the correctness reviewer's.
- Dangerous calls. Competing: 007's scanner rules for Python and JavaScript and this reviewer's Python section. Winner: the security reviewer keeps them all; nothing here needs an attacker.
- Concurrency and resource hazards by language. Competing: the codebase-audit-suite concurrency, resource-lifecycle and runtime-performance workers (628, 654, 653) and the correctness reviewer's resource-release and race bullets. Split: where the hazard is a rule of a language or framework (a Go map, a Python coroutine, a Node pool, a Spring transaction) it is written here, with the source's own severity tiers; a race or leak that needs no language rule is the correctness reviewer's.
- Persistence settings. Competing: ln-651, ln-652 and ln-654 (SQLAlchemy sessions, pools, bulk operations) and the correctness reviewer's transaction and query bullets. Split: library behaviour (what `expire_on_commit`, `pool_pre_ping`, `session.add_all` or `async with session.begin()` do) is here; whether the business operation is atomic is the correctness reviewer's.
- Dependencies. Competing: ln-625 (outdated, unused, native, custom, vulnerable), agent-skills dependency discipline and the security checklist (lockfiles, install scripts). Split: the fit of a dependency to the stack, its version, its upgrade hygiene and the lockfile as an artefact are here; advisories, install scripts, typosquatting and provenance are the security reviewer's.
- Idiom and modernisation. Competing: the audit suite's code-efficiency criterion and 'more idiomatic approach' prompt, and the code quality reviewer's style items. Winner: here, at the lowest level and only where the shorter form is as clear; verbose code kept on purpose is not a finding.
- Build output and ignore files. Competing: ln-646 (project structure) and the compliance and architecture reviewers. Split: what a given stack produces and must ignore is here; directory layout and naming by stack are the architecture and compliance reviewers'.
- Confidence thresholds. Competing: the feature-dev reviewer's filter at 80 and the code-review command's rubric. Winner: the five anchors, as before; both sources agree that unverified or stylistic findings are dropped.
- Confidence scale. Competing: `ce-code-review` anchors (`subagent-template.md` 59-69: "Pick the single anchor whose criterion you can honestly self-apply"), `pr-review-toolkit` 0-100 bands (`code-reviewer.md` 24-32: "Only report issues with confidence >= 80"), `security/security-reviewer` float floor (18-26), `security/007` impact-by-probability matrix (`stride-pasta-guide.md` 389-395) and the brooks-lint strictness presets (`common.md` 210-221). Winner: the `ce-code-review` anchors, because they are the same five values as the contract and each has a behaviour the reviewer can check itself against; a continuous score invites false precision.
- Shape of a finding's explanation. Competing: `ce-code-review` (`subagent-template.md` 112: "Lead with observable behavior") and brooks-lint's Iron Law (`common.md` 9: "Symptom, Source, Consequence, Remedy"). Winner: the `ce-code-review` rule, because the contract has one `description` field and the reader needs the effect first; the brooks requirement that a consequence be stated is kept inside it.
- Scope of a review. Competing: `ce-code-review` tiers (`diff-scope.md` 41-53), thermos (`thermo-nuclear-review/SKILL.md` 15-18: "ONLY report issues related to code that is being ADDED or MODIFIED") and `pr-review-toolkit` (`code-reviewer.md` 12, unstaged diff by default). Winner: `ce-code-review`, because it alone says what to do with an untouched line the change breaks; thermos would drop it.
- Intended changes. Competing: `ce-code-review` (`subagent-template.md` 136: check comments and commit messages for intent) and thermos (`thermo-nuclear-review/SKILL.md` 35-36, the intended-breakage exemption with its limits). Winner: thermos, because it also says when the exemption stops applying.
- Division of labour. Competing: `multi-agent-review` (six lens names, 30-37), thermos (two remits, `thermos/SKILL.md` 16-18) and the `ce-code-review` adversarial persona (80-91, a per-owner list). Winner: the `ce-code-review` list as the model, because it names an owner for each kind of defect; the other two are cited.
