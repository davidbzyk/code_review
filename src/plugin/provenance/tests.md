## Overlaps resolved

- Finding a gap. Competing: `ce-code-review` testing persona (7-17), `pr-review-toolkit` test analyzer (15-19: "Untested error handling paths that could cause silent failures") and brooks-lint T5 (171-177: "Happy-path only: no sad paths, no null/empty/zero inputs"). Winner: the `ce-code-review` persona for the list, because each entry is a code shape with a way to check it; boundaries and concurrency are added from `pr-review-toolkit`, side effects and legacy code from brooks-lint.
- Ranking a gap. Competing: `pr-review-toolkit` 1-10 criticality (42-47), brooks-lint three tiers per risk (for example 151-153) and the `ce-code-review` P0-P3 scale. Winner: P0-P3, because the contract requires it; the `pr-review-toolkit` scale supplies the meanings. Its own inconsistency (7-8 called important in one place, 8-10 critical in another) is resolved by treating 9-10 as P1.
- Mocks. Competing: `ce-code-review` (11: a mock that supplies the result under test) and brooks-lint T4 (132-139: counts and ratios). Winner: `ce-code-review` for the false-confidence case, because it is about what the test proves; the brooks-lint numbers are kept as a prompt to look.
- Suite health. Competing: brooks-lint T6 and its test guide (suite map, pyramid, run time) against the change-scoped sources. Winner: change scope; suite-level shape cannot be quoted from a change and is listed under never-report.
- Missing tests against over-testing. Competing: `pr-review-toolkit` test analyzer and `ce-code-review` (find untested paths) against the `codebase-audit-suite` risk-based guide (skip tests below priority 15, no coverage targets, no unit tests of what an end-to-end test covers). Winner: both, in different groups. A gap is ranked by cost times likelihood, and tests that earn nothing are reported only when the change adds them; the 'where a missing test costs most' list says which is which.
- Performance tests. Competing: `comprehensive-review` (review load testing and benchmarks; performance-critical paths need tests) against `codebase-audit-suite` (performance, load and stress tests do not belong in the correctness suite). Winner: neither outright. A benchmark apart from the correctness suite is fine; a throughput measure inside it is noise; the skill tells the reviewer to say which it applied.
- A test that disagrees with the code. Competing: `codebase-audit-suite` ln-630 ('code is truth, update the test') against its own risk-based guide ('the test is the specification; suspect the code'). Winner: intent decides; the skill gives both readings and says which applies when.
- Where tests live. Competing: `codebase-audit-suite` ln-637 and ln-646 (layout inconsistency and placement are findings) against `ce-code-review` (co-location against a test directory is a team convention). Winner: placement is reported only when the change breaks the project's own prevailing layout or leaves an orphan; a preference is not.
- Suite shape. Competing: `brooks-lint` (70:20:10, over ten minutes) against `agent-skills` (80:15:5) and `ln-632` (do not enforce ratios). Winner: shape is not quotable from a change; only what the change adds is reported, and ratios are never a finding on their own.
- Confidence scale. Competing: `ce-code-review` anchors (`subagent-template.md` 59-69: "Pick the single anchor whose criterion you can honestly self-apply"), `pr-review-toolkit` 0-100 bands (`code-reviewer.md` 24-32: "Only report issues with confidence >= 80"), `security/security-reviewer` float floor (18-26), `security/007` impact-by-probability matrix (`stride-pasta-guide.md` 389-395) and the brooks-lint strictness presets (`common.md` 210-221). Winner: the `ce-code-review` anchors, because they are the same five values as the contract and each has a behaviour the reviewer can check itself against; a continuous score invites false precision.
- Shape of a finding's explanation. Competing: `ce-code-review` (`subagent-template.md` 112: "Lead with observable behavior") and brooks-lint's Iron Law (`common.md` 9: "Symptom, Source, Consequence, Remedy"). Winner: the `ce-code-review` rule, because the contract has one `description` field and the reader needs the effect first; the brooks requirement that a consequence be stated is kept inside it.
- Scope of a review. Competing: `ce-code-review` tiers (`diff-scope.md` 41-53), thermos (`thermo-nuclear-review/SKILL.md` 15-18: "ONLY report issues related to code that is being ADDED or MODIFIED") and `pr-review-toolkit` (`code-reviewer.md` 12, unstaged diff by default). Winner: `ce-code-review`, because it alone says what to do with an untouched line the change breaks; thermos would drop it.
- Intended changes. Competing: `ce-code-review` (`subagent-template.md` 136: check comments and commit messages for intent) and thermos (`thermo-nuclear-review/SKILL.md` 35-36, the intended-breakage exemption with its limits). Winner: thermos, because it also says when the exemption stops applying.
- Division of labour. Competing: `multi-agent-review` (six lens names, 30-37), thermos (two remits, `thermos/SKILL.md` 16-18) and the `ce-code-review` adversarial persona (80-91, a per-owner list). Winner: the `ce-code-review` list as the model, because it names an owner for each kind of defect; the other two are cited.
